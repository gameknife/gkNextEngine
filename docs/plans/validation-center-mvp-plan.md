# 验证中心 MVP 开发计划

## 1. 目标与交付边界

让用户在 `gnb dashboard` 的「验证」页关注 agent 的后台验证：知道正在验证什么、看到失败原因和截图、选择可见重跑，并保留问题记录。**第一阶段就交付可运行的页面，不先建设完整测试平台。**

本文件是开发计划，以下新增页面、命令和存储格式均尚未实现。实现顺序为 M1 → M2 → M3；每阶段都应独立演示。

MVP 只接入 `gnb validate` 与 `gnb shot`，涵盖现有 `*.smoke.agentscript.json`。无需批量改写现有脚本，也不改变「gnb 解释脚本、NextValidation 提供原语」的边界。

| 纳入 MVP | 后续再做 |
|---|---|
| CLI 运行自动登记，Dashboard 未启动也留档 | `gnb smoke <package>`、VisualTest、Catch2 的统一接入 |
| 正在运行、运行历史、失败/待审阅筛选 | 跨运行问题去重、负责人、通知、完整工单流转 |
| 步骤、失败原因、日志、现有截图 | 视频录制、持续图像流、运行中显示隐藏窗口 |
| 启动时可见、终态运行可见重跑 | 暂停模拟、单步、变速、人工接管 |
| 人或 agent 给一次运行记录视觉问题 | 自动看图、图像阈值门禁、baseline 管理 |
| 本地目录持久化与轻量轮询 | 数据库、常驻调度服务、跨机器同步、GPU 队列 |

本阶段的“观察”是**步骤与截图浏览 + 可见重跑**。页面应明确这一能力边界，不把截图预览称为直播；也不宣称完整 smoke 体系已统一。

## 2. 用户看到的第一版

「验证」页沿用现有 Dashboard 的 Go template + htmx，不增加前端框架。

- 顶部：运行中数量、失败数量、待审阅/发现问题数量；筛选 target、状态。
- 左侧：按开始时间倒序的运行列表，显示名称、target、发起说明、状态、耗时、当前步骤。
- 右侧：选中运行的详情，先展示失败原因或问题备注，再展示步骤、截图缩略图和可展开日志。
- 终态运行提供「后台重跑」「可见重跑」；成功也可重跑，方便观察很快完成的 smoke。
- 详情地址包含 `runId`，刷新后保持选中；CLI 输出 runId、证据目录，方便 agent 引用。
- 新运行自动出现；页面每约 1 秒轻量刷新运行状态，截图只显示已经完成的产物。

空页面应给出一条现有 smoke 命令作为起点。最新列表先展示 50 条并支持继续加载；日志默认只读尾部，另提供完整日志下载，避免每秒读取全部历史。

## 3. 最小实现方案

### 3.1 独立运行目录是数据源

新增 `tools/gnb/internal/validationstore/`，只负责记录的创建、读取、原子更新和产物定位。CLI 与 Dashboard 共享该包，Dashboard 不成为运行所必需的服务。

建议目录：`out/build/<preset>/validation_runs/<runId>/`。runId 使用时间前缀加随机后缀，不依赖脚本名唯一。

```text
<runId>/
  run.json          # 元数据、运行状态、逐步结果和产物索引
  runner.log        # 子进程 stdout/stderr 与执行器诊断
  script.json       # 本次解析的脚本快照；shot 保存合成步骤
  screenshots/      # 每次截图使用步骤序号生成唯一名称
  review.json       # 人/agent 的审阅结论，与 runner 写入分开
```

MVP 暂不增加事件总线或事件文件：步骤开始/完成与收尾时原子替换 `run.json`，运行中低频更新心跳；日志顺序写入。读取中遇到临时失败保留上次快照，损坏记录显示“记录不可读”，不使整个页面失败。

最小字段：`schemaVersion`、`runId`、`kind`、`name`、`target`、`preset`、`reason`、脚本来源、有效参数、git HEAD/dirty、开始/结束/心跳时间、runner PID、状态、当前阶段/步骤、退出码、错误、步骤结果、截图相对路径。步骤保留原始描述、query/op/expected/actual、开始时间与耗时。

有效参数以数组保存，重跑使用结构化进程参数，不拼接 shell。保存可见性、viewport、scene、同步验证等配置；一次性控制 token 不写入可重放参数或公开日志。HEAD/dirty 只用于识别版本，不承诺恢复旧二进制或旧资产。

### 3.2 先把结果写对

- 在读脚本、检查可执行文件之前建立运行记录；坏 JSON、缺少程序、启动/连接失败都进入该次记录。
- 执行器统一收尾：检查步骤、进程退出、必需截图落盘后才能进入成功终态；任何失败都必须保留非零 CLI 退出码。
- `status` 最小集合：`running / passed / failed / canceled / interrupted`。失败另记 `phase` 与原因，例如 parse、launch、connect、step、exit、artifact，不为每种错误扩张状态枚举。
- `shot` 的 `passed` 在 UI 显示“采集完成”；validate 显示“脚本检查通过”。有截图的运行默认待审阅，不能把机器通过显示成“画面正确”。
- 运行中持续刷新心跳。心跳过期只提示“失联待确认”；确认 runner 不存在后才显示 interrupted，PID 不能单独作为仍在运行的证明。未知中断不伪装成引擎崩溃。
- Ctrl+C 贯穿启动、轮询、RPC 和进程清理；确保子进程回收。用户直接强杀 runner 时依靠失联识别，不承诺还能写完整最终报告。
- 记录目录创建失败时直接报错，不能静默执行一场不会留下记录的验证。

### 3.3 证据与现有命令兼容

- 实际截图输出重定向到本次运行的绝对路径，复用现有 screenshot 原语。步骤成功后可向脚本原路径复制兼容副本；历史记录只引用独立证据。
- 保留 `shot` 的固定 `agent_validation.jpg` 便捷副本和 validate 的旧报告/`--report` 输出，但都在最终结果确定后更新；旧路径不是历史数据源。
- 失败时保留已有截图与完整日志。控制通道仍可用时，尝试一次有短超时的失败截图；失败截图失败不能掩盖最初错误，进程已退出时直接跳过。
- 不导入旧报告，不做自动清理；页面给出证据目录，首版由用户手动清理已结束的运行。
- Dashboard 仅提供当前仓库运行目录内、已登记的日志/图片，校验相对路径与符号链接解析结果，不能将任意本机文件变成下载接口。

### 3.4 最小问题记录与重跑

审阅只做一份当前结论：`pending / accepted / issue`，附备注、作者、更新时间，可关联某张截图。默认有截图则 pending；没有截图时可显示无需视觉审阅，仍允许记录问题。审阅不能改写机器状态。

UI 提供“已看过，无问题”和“记录问题”。为 agent 提供小型写入入口，建议新增命令（尚未实现）：

```bash
gnb validation note <runId> --issue --message "角色穿过台阶，见第二张截图"
```

所有写入复用 store，`review.json` 原子更新；MVP 采用最后一次审阅覆盖当前结论，不建设评论系统。“待处理”筛选聚合机器失败、待审阅与已记录问题。

重跑从保存的脚本快照与有效参数创建新 runId，并记录 `rerunOf`；使用当前 preset 的二进制与当前资产，界面写明“按原脚本重新执行”，不称为历史录像或精确复现。旧失败、截图和审阅不会被新成功覆盖。

可见重跑复用 `--visible`，同时给 shot 补齐同一选项。选择可见重跑不会绕过 `--agent-validation` 的 Streamline/FidelityFX 等限制，页面以简短说明标出“验证模式”。第一版仅允许终态运行重跑，并在同 target 已有活动运行时禁止页面重复发起；跨 CLI 的全局并发调度留待后续。

## 4. 开发顺序：每步都有可见效果

### M1：一条 smoke 从终端进入页面

- [x] 实现最小 store、runId、run.json/script.json/runner.log，统一终态收尾。
- [x] 接入 validate 和 shot，独立归档截图，保存旧路径兼容副本。
- [x] Dashboard 增加「验证」tab：运行列表、详情、状态轮询、步骤、日志、截图。
- [x] CLI 打印运行身份和证据目录；可选 `--reason` 为列表提供一句验证目的，未传时显示脚本名。

**演示门槛：** 打开 Dashboard，在另一个终端运行现有 editor smoke；页面自动出现记录，结束后看到截图。关闭再打开 Dashboard 记录仍在，连续两次运行有两个独立条目。很短的脚本可以直接显示完成；运行中展示用有有限等待的演示脚本验证。

### M2：失败可信，问题有地方留下

- [x] 补齐坏脚本、缺程序、连接失败、断言失败、退出异常、截图缺失、Ctrl+C 的记录与诊断。
- [x] 加入低频心跳、失联展示与 interrupted 恢复识别；避免永远显示运行中。
- [x] 失败详情优先显示 query/op/expected/actual 与日志，尽力补一张失败截图。
- [x] 加入审阅状态、问题备注、`validation note` 与“待处理”筛选。

**演示门槛：** 用临时脚本制造确定的断言失败；页面能指出哪一步、期望和实际分别是什么，CLI 非零退出。agent 给截图记一条问题，刷新/重启 Dashboard 后仍能看到。下一次成功不会隐藏旧失败。

### M3：点击即可观察，完成 MVP

- [x] 后台重跑与可见重跑，复用脚本快照和有效参数，创建 `rerunOf` 关联。
- [x] shot 支持 `--visible`；按钮展示当前可用性，运行中不重复启动同 target。
- [x] 完善空态、筛选、日志尾部/下载和详情深链接。
- [x] 更新 `docs/guides/gnb-cli.md`、现行验证设计文档和 AGENTS 验证说明：运行前可填目的、结果引用 runId、视觉问题写入审阅记录。

**演示门槛：** 在已结束 smoke 详情点击“可见重跑”，窗口实际出现，新记录展示进度并关联旧运行。用户能浏览截图、标记问题，再从待处理列表找到它。

## 5. 验证与完成标准

以 Go 层改动为主，不进行 C++ 全量构建。若实现时确需修改 Engine/NextValidation，按 AGENTS 的影响范围构建，并另行验证该改动；优先保持现有控制协议。

自动验证使用临时目录和可控的假子进程/控制服务，不依赖 GPU 覆盖异常路径：

- store：重复脚本不覆盖、原子更新可读、审阅不覆盖执行状态、产物路径越界被拒绝。
- runner：启动失败也有记录；步骤通过后进程非零/截图缺失最终仍失败；取消回收进程；报告与退出结果一致。
- Dashboard：CLI 写入记录可发现，损坏记录不拖垮页面；重跑参数数组与脚本快照正确，旧运行保持不变。

运行相关 Go 包测试和 vet（`internal/validationstore`、`internal/validate`、`internal/dashboard`、`cmd/gnb`）；按现有构建入口编译 gnb，验证 Dashboard 的实际模板和路由。

人工验收只需：一次成功 smoke、一次受控失败、一次 shot、一次可见重跑，以及关闭/重开 Dashboard。受控失败脚本存入临时目录，不把永远失败的脚本加入正式 smoke；可见运行前告知用户。

MVP 完成必须同时满足：

1. agent 直接运行 CLI，无需 Dashboard 在线，稍后仍能看到记录。
2. 同名重跑不覆盖历史；截图与本次运行一致。
3. 启动失败、断言失败、异常退出不会出现新的绿色通过记录。
4. 一个页面能找到失败步骤、日志、截图及人/agent 的问题备注。
5. 可以主动可见重跑，清楚知道它是新运行、使用当前构建。

## 6. 后续与文档收口

# NextDayz Web 客户端开发计划

本文是 [Web 客户端架构设计](nextdayz-web-client-design.md) 的执行顺序。设计文档回答"做成什么样、
为什么"，本文回答"按什么顺序做、每一步怎样算完成、哪些事可以同时做"。术语（同源内核、烘焙、
表现层、端口）以设计文档为准。

## 0. 核对结果

设计文档第 3 节的 D1–D8 已于 2026-11-16 全部按推荐确认。下表记录各项结论落在计划的哪里；执行中若
有证据表明某项站不住（W0 的出口就是为此设的），停下交回核对，不自行改道。

| 结论 | 设计章节 | 在计划中的体现 |
| --- | --- | --- |
| 玩法走同源内核（WASM），不做 TypeScript 重写 | D1 | W3、W5、W6 按"拆分进内核"执行，不保留重写分支 |
| SCAD 走离线烘焙 | D2 | W2 |
| 传输走 WebRTC DataChannel；WebSocket 回退不进首版 | D3 | W1；回退传输列在"之后" |
| 界面用 DOM 重写，桌面与 Web 各维护一份 | D4 | W4-5、W7 |
| Jolt 同源编进内核 | D5 | W0-3 验证，W5-3 落地 |
| 首版只有联机，没有单机战役 | D6 | `WorldSim` 不进内核；单机列在"之后" |
| 公网上线前给 Master 加登录口令 | D6、7.3 | W8-0，W8-4 对外部署的前置 |
| 代码位置与命令命名 | D7 | 第 1 节的写入范围 |
| 桌面三大浏览器、键鼠、WebGL2 为验收基线 | D8 | W8-5 |

## 1. 工作线与写入范围

四条工作线，各自有明确的写入范围。**同一时间，一个范围只允许一个执行者写入。**

| 工作线 | 内容 | 写入范围 |
| --- | --- | --- |
| **A 服务端** | DS 的 WebRTC 传输、Master 的信令/托管/清单、机器人的 WebRTC 模式 | `src/Modules/NextNet/`、`tools/gnb/internal/dzmaster/`、`tools/gnb/cmd/gnb/`（`ds`、`master`）、`src/Application/Util/NextDayzBots/` |
| **B 烘焙** | `NextDayzBake` 与 `gnb web bake` | `src/Application/Util/NextDayzBake/`、`tools/gnb/` 下新增的 `web` 命令、`src/Modules/SceneExport/`（如需扩展导出） |
| **C 内核** | 把玩法代码整理成 `NextDayzCore`，建立 WASM 构建 | `src/Application/Game/NextDayz/`、`src/Gameplay/Rig/`、`src/Gameplay/Character/`、`src/Modules/NextPhysics/`、`src/Application/Web/NextDayzWebCore/`、CMake 预设 |
| **D 表现层** | Web 客户端 | `web/nextdayz/` |

两条特别规则：

1. **工作线 C 是串行的**，并且与桌面 NextDayz 的日常开发抢同一批文件。C 的每个任务开始前要与正在
   进行的 NextDayz 改动对齐；拆分大文件（`PlayerController`、`WeaponSystem`、`PlayerRigVisual`、
   `NextDayzNetwork.cpp`）的那几天，这些文件不接受其他改动。
2. A 与 C 都会碰到联机代码，但范围不同：A 只改 `NextNet` 模块内部，C 改 NextDayz 自己的联机逻辑。
   `FNetHost` 对游戏的接口在 W1 冻结，之后 C 不需要关心传输。

## 2. 贯穿全程的闸门

工作线 C 的每个任务、以及任何改到 NextDayz C++ 的提交，合入前必须通过：

```bash
./gnb.sh build NextDayz gkNextUnitTests NextDayzBots
```

```bash
./out/build/<preset>/bin/gkNextUnitTests "[NextDayz]"
```

```bash
./gnb.sh ds --bots 8 --minutes 3
```

再加上与所改子系统对应的 agentscript（在 `assets/agentscripts/` 下）：改 3C 跑
`nextdayz-3c-*`，改库存跑 `nextdayz-inventory-*`，改联机跑多人设计 §7 列出的 `nextdayz-net-*`
各组，改 Master 流程跑 `nextdayz-master-leave` 与 `nextdayz-master-return`。

W3 建立 WASM 构建之后，闸门增加两项：内核包含检查通过；`ndcore.wasm` 构建成功且协议金标一致。

## 3. 阶段总览

```
W0 技术验证 ──┬─► W1 传输与信令（A）────────┐
              ├─► W2 烘焙管线（B）──────────┤
              └─► W3 内核 I：数据与联机（C）─┼─► W5 内核 II：角色与 3C ─► W6 内核 III：战斗与物资 ─┐
                  W4 表现层 I：地图与大厅（D）┘        （C + D）                 （C + D）           │
                                                                                                    ▼
                                                              W7 界面补全（D）──► W8 全流程、部署、收尾
```

| 阶段 | 结束时能演示什么 | 规模 |
| --- | --- | --- |
| W0 | 三个最小实验各有结论，设计文档里的"需验证"全部回填 | 小 |
| W1 | 机器人经 WebRTC 连上 DS，与走 ENet 的机器人同服 | 中 |
| W2 | 训练场与洛克特烘焙完成，统计与桌面一致 | 中 |
| W3 | Node 里的 Web 机器人：登录 Master、出击、进服、拾取与丢弃通过账本、撤离 | 中 |
| W4 | 浏览器里登录、看仓库，在烘焙出的洛克特里自由漫游，昼夜随参数变化 | 中 |
| W5 | 浏览器里走、跑、蹲、跳、翻越；桌面与 Web 玩家互相看见对方的动作与服装 | 大 |
| W6 | 一起打感染者、互伤、抢物资、吃喝包扎；第一人称武器、特效、音效 | 大 |
| W7 | 完整界面：HUD、背包、地图、死亡、设置、撤离 | 中 |
| W8 | 公网上从网页完成"登录—出击—搜刮—下线—回归—撤离"，混合客户端的自动化全绿 | 中 |

规模是相对量："小"指一两个任务就能收尾，"大"指需要拆成多个各自可验收的任务。不给日历日期。

## 4. 各阶段任务

每个任务写明要做什么、落在哪里、怎样算完成。任务编号供派工时引用。

### W0 技术验证

三个实验互不依赖，可同时进行。代码可以是一次性的，但**结论必须回填到设计文档**对应的"需验证"处。

| 任务 | 内容 | 完成标准 |
| --- | --- | --- |
| W0-1 内核最小构建 | 用 Emscripten 编译 `NextDayzBots` 已经在用的那组文件（协议、库存、物品表），在 Node 里调用；选三到五种消息（含按内存布局写出的结构体）在桌面与 WASM 各编码一次 | 两边字节完全相同；记录所需的头文件整理清单、工具链安装方式、产物体积。若 wasm32 下结构体对齐与桌面不同，给出修正方案 |
| W0-2 WebRTC 传输实验 | 在一个独立小程序里用 libdatachannel 接受浏览器连接：两条 DataChannel（有序可靠 / 无序零重传）、一次往返的信令、公网候选 | 浏览器页面能收发两类消息；确认单个 UDP 端口能否承载多个对端、各浏览器协商的最大消息长度、3 KB 不可靠消息在 2% 丢包下的到达率；Node 侧是否有可用的 libdatachannel 绑定（供 Web 机器人使用） |
| W0-3 烘焙与加载实验 | 把训练场导出为 GLB + 碰撞网格，three.js 加载显示；把 Jolt 编成 WASM，用导出的碰撞让一个胶囊角色走起来 | 记录三角形数、文件体积、绘制调用数、加载耗时、帧时间；据此校正设计 8.1 的性能预算；确认碰撞体构建耗时 |

**出口**：三项结论写入设计文档；D1、D2、D3、D5 没有被实验否定。任何一项被否定，停下交回核对。

### W1 传输与信令（工作线 A）

| 任务 | 内容 | 完成标准 |
| --- | --- | --- |
| W1-1 `FNetHost` 多传输 | `FNetHost` 内部改为可挂多个传输，对游戏的接口不变；ENet 实现迁入第一个传输；链路模拟与流量统计移到传输之上 | 桌面联机行为无变化：第 2 节闸门全过 |
| W1-2 WebRTC 传输 | 第二个传输：通道映射、不可靠通道的序号前缀与乱序丢弃、可靠通道的大消息分块、每秒 ping 得到往返时延、回调线程只入队 | 单测覆盖：乱序到达只交付最新的不可靠消息；超过上限的可靠消息完整重组；200 ms / 1% 丢包下可靠消息不丢不乱序（与 ENet 传输同一组用例） |
| W1-3 DS 启用 | DS 增加 WebRTC 端口配置与长轮询取信令；`gnb ds --web` 额外开本机明文信令端口供开发直连 | DS 日志显示两种传输都在监听；不启用时行为与现在完全一致 |
| W1-4 Master 信令与派遣 | `/api/rtc/offer`、`/ds/signal`；为每个 DS 分配 WebRTC 端口并写进派遣结果；信令请求的账号与目标校验 | Go 单测：未登录、指向非本人派遣的 DS、超时，均被拒绝；正常路径一次往返拿到 answer |
| W1-5 机器人走 WebRTC | `NextDayzBots` 增加 `--transport webrtc`；`gnb ds --bots N` 可指定混合比例 | 8 个 ENet + 8 个 WebRTC 机器人同服 30 分钟，80 ms 延迟 + 2% 丢包：全部在线、无被拒、无掉线；服务器 tick 耗时与纯 ENet 的压测结果同一量级 |

到这里，"浏览器客户端在协议与规则上与桌面等价"已经被自动化证明，尽管还没有画面。

### W5 内核 II：角色与 3C（工作线 C + D）

这是对桌面代码改动最深的阶段，分成四个可以各自验收的任务，按顺序做。

| 任务 | 内容 | 完成标准 |

训练场 Web 验收页为 [本地 4181](http://127.0.0.1:4181/)。「前往障碍场」将本机验收用的幸存者放到
第一道木墙前。Chrome 真机端通过键鼠完成跑、慢走、冲刺、蹲、第一和第三人称切换、撞墙阻挡及翻越，

P95 均为 16.7 ms，均衡档共 434 次绘制。设计 8.1 指定的独显笔记本仍需单独验收。
桌面端翻越、相机臂、自由观察、瞄准后坐和基础穿衣脚本通过。W7 收尾时在平地夹具上复验了冲刺动画，
冬装脚本加入能容纳冬季衣物的临时背包后通过。W6 共用了感染者命中盒构造和装备配件挂点，第三人称
程序化姿态仍有差异。

## 5. 派工建议

- **W0 的三个实验**可以交给三个执行者同时做，互不写同一处。
- **W1、W2、W3、W4 四个阶段**分属四条工作线，可同时推进。其中 W3-5 需要 W1 完成，W4-6 需要 W3-5
  完成，W4-2 需要 W2 至少产出训练场。
- **W5、W6 的内核任务**（W5-1 到 W5-3、W6-1 到 W6-3）只能由一个执行者按顺序做；对应的 Web 任务
  （W5-4、W6-4、W6-5）可以由另一个执行者紧跟着做，接口以内核的帧状态为准。
- **W7** 在 W6-3 之后即可开始，与 W6-4、W6-5 同时进行。
- 每个任务完成时在提交说明里写明跑过的闸门与结果；内核任务还要写明"哪些文件被拆分、桌面适配层
  留在哪里"，方便下一个执行者接手。

仓库的任务调度以 `.spec/TODO.md` 为准。本计划已核对，可按上面的任务编号录入其中；录入之前不视为
已授权执行。

## 6. 每个阶段的完成定义

一个阶段只有同时满足以下几条才算结束：

1. 表中每个任务的完成标准都有可复现的证据（命令输出、测试结果、截图）。
2. 第 2 节的闸门全部通过，桌面 NextDayz 可正常构建与联机。
3. 新增的自动化测试已接入 CI 或有明确的手动运行命令。
4. 阶段中发现的、与设计文档不一致的事实，已经改进设计文档，而不是只留在提交记录里。
